## 0. 产品范式：从"工具问答"回到"发消息"

| | ChatGPT 式（现状） | 微信式（目标） |
|---|---|---|
| 发送权 | 回复完成前输入被禁用 | **永远可发** |
| 连发几条短句 | 不可能 | 正常行为，角色看完一起回 |
| 打断 | 无中止手段 | 点停止只是保险丝，不是日常操作 |
| 心理模型 | 向工具提交请求 | 和人聊天 |

角色扮演伴侣应用的自然形态是后者：真实的人不会"禁用输入框"，只会把你连发的
三条一起读完再回一句。

## 1. 目标行为规范

1. **发送永远可用**：任何时刻点发送，消息立即成为气泡（乐观 UI）。
2. **收口合并**：角色尚未开始回复时又发的消息，与前者合并为一轮——角色一次性
   回应全部。收口窗口：最后一条用户消息后静默约 2 秒。
3. **排队**：角色正在生成时新到的消息进入待发队列，以"待发送"样式显示；
   当前回复完成后自动进入下一轮，无需用户任何操作。
4. **停止 = 保险丝**：仅在生成失控（跑偏/卡死）时手动使用，入口弱化为
   流式气泡上的小图标即可，不属于主交互。
5. （Phase B 解锁）**服务端防抖与主动消息**：见 §3.4。

## 2. Phase A —— 前端排队（零后端改动，~1 天）

纯客户端改造，后端 API 一行不动。

### 状态机

```
idle ──send──► streaming ──done──► [队列非空?] ──是──► 收口等待(≤2s) ──► 自动批量发送 ──► streaming
  ▲                                │否
  └────────────────────────────────┘
```

### 细节

- 流式期间发送的消息进入 `pendingQueue`（Redux），渲染为半透明气泡 +
  "待发送"角标；
- 当前流 `done` 后取队列：若最后一条入队距今 < 2 秒，继续等到 2 秒收口；
  队列内所有消息文本以换行拼接为**一次** `sendMessage` 调用（模拟"看完
  一起回"）；
- 流式失败/中断：pendingQueue 原地保留、恢复可编辑，不自动重发；
- 输入框在任何状态下都可打字、可追加附件；
- 附件同样允许排队，随所在批次一起发出；
- 首条消息（开场白场景）不参与合并，保持现有 `start_conversation` 语义。

### 改动面

`ChatInterface.tsx`（发送守卫与队列调度）、`ImmersiveChatWindow.tsx`
（移除 `disabled={isLoading}` 冻结、待发送气泡样式）、`chatSlice`
（`pendingQueue` 状态）。`api.ts` 不动。

## 3. Phase B —— 异步生成架构（架构级里程碑，独立大项）

### 3.1 目标拓扑

```
┌──────────┐  POST send_message（毫秒级返回）   ┌────────────────────────────┐
│  前端     ├──────────────────────────────────►│ 保存 user_message          │
│ (任意时刻 │                                    │ 入队 generate_reply_async  │
│  可发送)  │◄──────SSE /sessions/{id}/events───┤        │                   │
└──────────┘   token 增量 · 完成 · 中断事件       └────────┼───────────────────┘
                                                          ▼
                                              Celery worker 内生成回复，
                                              每 chunk 发布到 Redis 频道
                                   chat:reply_stream:<session_id>（复用记忆
                                   事件总线的 pub/sub 模式），并增量落库
```

现状的痛点：生成与 HTTP 连接绑死（一条消息占住一个请求直到流结束），
这使"随时发消息""断线续读""主动消息"都无法成立。

### 3.2 关键组件

1. `POST send_message` 轻量化：只保存消息 + 入队，立即返回 `message_id`；
2. 新任务 `generate_reply_async(chat_session_id, trigger_message_id)`：
   生成 → 逐 chunk 发布到 Redis 频道 + 增量更新 `ai_message` 行（每 N chunk
   或每秒一次，`update_fields=['content']`）→ 完成时走既有
   `_finalize_ai_response`（token 统计、标题、记忆提取全数复用）;
3. 订阅端点 `GET /api/sessions/{id}/events/`：SSE 长连接，桥接
   `chat:reply_stream:<sid>` 与 `chat:memory_updates:<sid>`（同一总线两种事件）；
4. **增量持久化 + 中断标记**：`Message.interrupted BooleanField(default=False)`；
   worker 收到取消信号或检测订阅方全断时，保存已生成部分并置位；
5. 断线重连：前端重连 SSE 后先 `GET messages?after=<id>` 补拉快照，再续订；
6. 服务端防抖（v2 可选）：worker 启动前检查会话最近 2 秒是否还有新消息，
   有则顺延，天然支持"连发等你说完"。

### 3.3 停止键

Phase B 中停止 = 向频道发布一条 cancel 控制（或直接删除去重键使任务提前
收尾），后端保存半截内容并标记 interrupted；前端按钮常驻于流式气泡角落。

### 3.4 免费解锁的能力

- **主动消息**（AnySoul heartbeat 式）：既然生成已是后台任务，beat 定时器
  可以让角色在无输入时自主发起对话——伴侣应用的核心卖点之一；
- 输入中指示器、多端同步、离线消息补拉，均随推送通道自然获得。

## 4. 与记忆系统的互操作

- 提取 prompt 的 NEW TURN 段本就取最近 6 条消息（`_format_messages_for_prompt`），
  一轮含多条用户消息无需任何适配；
- 合并无冲突：合并轮在记忆视角就是普通一轮；
- 中断轮语义：只要 AI 已生成的部分有实质内容就照常参与提取；
  `interrupted=true` 作为附加上下文透传给提取 prompt（可选增强）；
- 记忆写入仍经 `_dispatch_memory_sync`，与聊天异步化正交。

## 5. 风险与开放问题

| # | 问题 | 倾向 |
|---|------|------|
| 1 | worker 全下线时的降级 | eager 设置已验证可行：退化为进程内同步生成 |
| 2 | SSE 双通道（reply + memory）合流后的心跳/重连参数 | 实施时定 |
| 3 | topic / chat 两模式下会话切换时的订阅生命周期 | 订阅 key 按 session，切会话即换订 |
| 4 | token 用量统计依赖 finalize，增量路径需保证 finalize 必达（at-least-once + 幂等） | 任务重试幂等设计 |
| 5 | Phase A 的合并拼接对附件-only 消息的表示 | 占位符文本"[图片]"/"[文件]" |

## 6. 明确不做

- 同一会话内的并行生成（两条回复交错出现）——永远不做，违反对话直觉；
- WebSocket 升级——SSE 已满足单向推送需求，避免引入新的连接管理栈。

## 8. Phase C —— 实时语音（TTS 已实现；输入侧已随 v0.1.3 落地）

> v0.1.3 实时模式现状：进入实时模式后持续聆听（自适应 VAD 断句，无按键），
> 说完自动转写发送、流式回复后继续聆听——即"说话会对应回复"。
> ASR 走服务端 CPU faster-whisper（int8，按句分段 HTTP），摄像头帧作为
> 图片附件走既有多模态管线，让角色"看到"用户。本节记录 TTS 与全双工
> 方向的设计与落地情况。

### 8.1 TTS 落地（2026-08-24，Genie-TTS 路线）

- **引擎选型**：纯 CPU 约束下否决 GSV 官方推理/IndexTTS/ChatTTS（RTF≫1
  或许可冲突），采用 **Genie-TTS**（GPT-SoVITS 的 ONNX 推理引擎，MIT）：
  把已训练的角色音色（如圣亚 `Seia_e8_s240.pth`+`.ckpt`，V2ProPlus）转换为
  ONNX，CPU 首响 ~1.1s 量级、RTF≈0.9-1.2（i7 级笔记本实测）。
- **架构**：TTS 引擎一律以独立 HTTP 服务运行，Django 只做客户端
  （`chat/tts.py`），三种 provider 可切换：
  * `genie`（默认）—— Genie FastAPI（/load_character → /set_reference_audio
    → /tts 返回 32kHz/16bit/mono 裸 PCM，Django 侧包 WAV 头）；
  * `gptsovits` —— 官方 api_v2，支持 v2/v2pro/v2proplus/v4 全部四种模型
    版本（CPU 实时性差，留给有 GPU 的场景）；
  * `indextts` —— 预留 HTTP 客户端。
- **上游 bug 补丁**：genie 的中文声调连读（ToneSandhi）对「嗯」等无韵母字
  `[-1][-1]` 越界、返回空音频——`backend/scripts/patch_genie_tonesandhi.py`
  幂等修复，重装后需重跑。
- **前端交互**：聊天头部「语音回复」开关（localStorage 持久）；回复 done
  后按句切块（~80 字符）顺序合成播放，首句先出声；新回合/关闭开关即停。

### 8.2 届时的目标交互（动工前评审）
