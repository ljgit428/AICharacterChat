# Version 0.1.5 - Streaming Replies That Persist, Live System Think & Reply/Heart-Voice Pipeline Split

## Release Date
September 2026

## Overview
Version 0.1.5 makes the streaming reply a first-class persisted object and rebuilds the reasoning pipeline around it. Replies now land in the database chunk by chunk while they are being generated (`Message.status` lifecycle + a streaming reply draft), so closing the page mid-generation no longer loses what was already written. The model's native reasoning stream is displayed live as system think, and the per-round character heart-voice (角色心声) is no longer demanded from the model via a marker protocol — it is generated by a dedicated follow-up call after the reply finishes, which removes the recurring "plan text / protocol tags leaking into the reply" pollution. The chat window header is compacted to reclaim vertical space, legacy history messages are unified onto the ReAct timeline renderer, and the character avatar upload bug (silent missing URL) is fixed. Startup docs switch to uvicorn (ASGI) because WSGI buffering made streaming look like one delayed blob.

## ✨ New Features

### Incremental Reply Persistence (write the reply to the DB as it streams)
- **`Message.status` lifecycle** (migration `0050_message_status`): `''` = completed, `streaming` = being written right now, `interrupted` = the turn failed but the partial reply was kept. The status flows through the event payload (`assistant_message_payload(status=…)` in `events/types.py`), the projection (`events/projection.py`) and the API serializer, so `rebuild_session_messages` stays lossless.
- **`_StreamingReplyDraft`** (`backend/chat/tasks.py`): at turn start an empty `assistant/message` event with `status='streaming'` is appended and projected into a `Message` row; every `delta` / `thinking` / `tool` fragment then updates that same event and row in one transaction ("每出来一段就记一段"). On success `_finalize_ai_response` completes the final fields and clears the status; on failure `_finish_draft_after_failure` keeps what was generated as `interrupted`, or discards the draft entirely if nothing was produced. A client disconnect (`GeneratorExit`) is deliberately not an error: the stream simply stops and everything already written stays.
- **Incomplete-reply markers**: history loaded with `streaming`/`interrupted` rows renders an amber marker under the bubble —「这条回复未完成（生成已中断，保留了已生成的部分）」/「这条回复被中断（保留了已生成的部分）」— so a page closed mid-generation leaves a readable partial reply instead of a ghost.
- **E2E coverage** (`backend/chat/tests/test_e2e.py`): partial reply persists after the page closes; failure marks the row `interrupted` and keeps partial content; a failure that produced nothing discards the draft.

### Live Thinking Stream (system think visible while generating)
- **Tool-loop SSE streaming** (`_stream_openai_compatible_round`): each ReAct round opens a real SSE stream instead of waiting for the whole round — reasoning increments arrive and are forwarded within the round, tool-call name/argument fragments are accumulated in place. Previously the whole round finished first and all its thinking appeared at once ("一股脑").
- **UTF-8 enforced on SSE decoding**: OpenAI-compatible endpoints often omit `charset` in the content type, so `requests` fell back to ISO-8859-1 and Chinese reasoning turned into mojibake; the stream reader now sets `response.encoding = 'utf-8'` explicitly.
- **`_DualThinkingSplitter` as a defensive layer**: marker scanning now applies in every state and each tool-loop round can repeat the `<character_os>` / `<raw_reasoning>` markers independently; the no-marker fallback streams thinking through live instead of buffering ~1200 chars and emitting it once. In the main pipeline the model is no longer asked to emit any markers (see below), so the splitter mainly guards against providers that still leak tagged reasoning.
- **Frontend streaming timeline**: `updateMessageSteps` (new `chatSlice` action) lets `ChatInterface` build the「思考 · 第 N 轮 → 工具」steps on the placeholder message as the stream arrives, instead of showing the full list only after `done`. Round changes flush the accumulated thinking into a new step row; the `done` event then replaces the placeholder with the server message.

### Reply / System-Think / Character-OS Pipeline Split
The v0.1.4 dual-block protocol — asking the model to write both a character monologue and raw reasoning into its reasoning stream with `<<<CHARACTER_OS>>>` / `<<<RAW_REASONING>>>` markers — is retired. Models followed it sporadically and kept writing plans and monologues into the visible reply. The new architecture:

- **System prompt**: the protocol block is replaced by a single **REPLY PURITY** section — the reply must be only the character's spoken lines, with a concrete negative example forbidding the「分析用户输入 → 规划回复 → 风格检查」plan text the model kept emitting. Internal markers are unified to XML (`<character_os>` / `<raw_reasoning>`), used only by the backend; no prompt asks the model to output tags anymore.
- **System think**: the main generation's native reasoning stream (no protocol markers) is streamed live to the frontend as the system think and persisted as `raw_reasoning`.
- **Character OS (角色心声) as a follow-up call**: after the reply has fully streamed, `_generate_character_os` feeds the collected system think back to the model (`_build_character_os_prompt`) and asks for a short first-person in-character Chinese inner monologue — streamed live as thinking events so the user watches it arrive; on failure it is left empty and the frontend degrades to showing the system think alone.
- **Steps shape**: `Message.steps` now keeps only the tool calls plus **one** final thinking step (`text` = character OS, `raw_text` = the full system think), rendered with the existing【角色心声 | 原始推理】switcher. Per-round system think remains visible live during streaming but is not persisted as per-round rows.
- **Reply cleaning** (`_extract_real_reply_text`): strips thinking-variant tags (`</thinking>`, `<character_os>`, `<raw_reasoning>` variants — replies were observed starting with a bare `</thinking>`), drops protocol paragraphs and「回答/回复 × 口吻/语气/方式」self-instruction prefixes, and trims plan-prefixed openings, while leaving persona-led replies untouched.

### Unified Thinking Display for Legacy History
Old messages recorded before `Message.steps` (pre-v0.1.4 history) previously rendered with the old single-block「思考过程」layout. `AgentSteps` now synthesizes standard steps from the message-level `thinking`/`rawReasoning` plus tool calls (one thinking step + tool sequence), so all history shares the same timeline renderer (「思考 · 第 N 轮」 rows with the dual-mode switcher); tool rows are titled uniformly through `describeToolCall`. The old single-block branch is deleted.

### Compact Chat Header (more vertical space for messages)
The chat window's own header — the「对话空间」label, the「正在与 X 对话」title and the「N 条消息」pill — duplicated the outer app bar's avatar + character name. It was removed from `ImmersiveChatWindow`, so the message list starts directly at the top of the window and every turn gains the full header height. The conversation identity remains visible in the outer app bar.

## 🐛 Bug Fixes
- **Character avatar never displayed after upload**: the character-creation form uploaded avatars through `/files/upload/` (a staging endpoint) whose response contains no URL field, so the preview and the saved character both ended up with `undefined`; the form now uses the `/upload/` endpoint (avatars bucket, immediate persistent URL), the same one the user-settings page uses.
- **Thinking "appeared all at once"**: non-streamed tool rounds emitted their reasoning only after the whole round completed; now every increment is forwarded the moment it arrives.
- **Chinese mojibake in streamed reasoning**: SSE bodies without an explicit charset were decoded as Latin-1; UTF-8 is now forced.
- **System think / plan text polluting the reply body**: plan prefixes, protocol paragraphs, stray `</thinking>`-style tags and「回答/回复 × … 口吻/语气/方式」self-instruction blocks are stripped from the visible reply; the protocol that invited this pollution was removed from the prompt.
- **Two stale tests** that lagged the implementation (round numbering fields, thinking protocol assumptions, real-network mocking) were updated to the current pipeline.

## 🗂 Not Included / Backlog

### Cross-Window Realtime Chat Sync (implemented & verified, then reverted)
**Motivation**: when the same app is open in two windows (e.g. the /chat page in two tabs) and a message is sent from one window, the other window should update immediately — including the live streaming reply.

**What was built (reverted, not on this release)**:
- `frontend/src/utils/chatSync.ts` — a `BroadcastChannel`-based layer (same-origin, same-browser; no backend change): `publishChatEvent` / `subscribeChatEvents` (SSR-safe singleton channel) plus `applyChatSyncEvent`, which maps broadcast events back to Redux actions with message-id deduplication and strips `blob:` URLs (they are window-scoped and would render as broken previews in the other window).
- Broadcast points wired into `ChatInterface.handleSendMessage` — every store mutation is mirrored: optimistic user message, streaming assistant placeholder, `delta` / `thinking` / `tool` increments, server-message replacement (`session` event), final message replacement (`done`), abort/error paths, `setLoading`, and session updates.
- Receiving side: `ChatInterface` subscribes once per conversation and applies events only when `characterId` and `sessionId` match its active conversation (both-open-fresh conversations are mirrored too, via the null-session rule). A `sessionId` ref mirrors the state that stream closures cannot see.

**Verification (before revert)**: two live windows with the same character conversation open — the user message appeared in the second window instantly with name/timestamp/avatar, the「停止」button (loading state), the thinking timeline and the final reply all mirrored while streaming, and no duplicates appeared in either window (BroadcastChannel does not echo to the sender, plus id-based dedupe). Both windows end with identical message lists; history on refresh still comes from the server.

**Why reverted**: not a top-priority feature for v0.1.5; the change was dropped to keep the release diff focused. The sync points are self-contained (one util module + hotspots inside `handleSendMessage`), so the implementation can be revived from these notes. Note the scope limit: BroadcastChannel only covers same-browser windows; true cross-device sync would need server push (SSE/WebSocket).

### Avatar Image Description into the Memory System (confirmed, not yet scheduled)
Recorded in `docs/requirements-tracking.md` (found while fixing the avatar upload bug): character avatars are currently display-only (`avatars/` bucket, `avatar_url` field) with no content semantics — the model cannot see or describe the character's appearance. Desired: on avatar upload, generate an LLM image-description text (appearance, clothing, mood) alongside the URL, store it (e.g. `avatar_description`), expose it via `CharacterSerializer`, and inject it into the character setup (e.g. `build_character_setup_markdown`) so the character "knows" its own looks and the memory system can reference it as a fact. Suggested implementation reuses the existing vision input pipeline (`image/*` including webp is already whitelisted in `chat/tasks.py`).

## 🛠️ Technical Notes
- Backend (`backend/chat/tasks.py`): `_StreamingReplyDraft` + `_finish_draft_after_failure` (incremental persistence and failure semantics), `_stream_openai_compatible_round` (per-round SSE with UTF-8 decode and tool-fragment accumulation), `_dual_thinking_protocol_text` (REPLY PURITY section), `_build_character_os_prompt` / `_generate_character_os` (end-of-turn heart-voice call, streamed as thinking events), `_DualThinkingSplitter` (marker scan in all states, per-round marker re-entry, no-marker live-stream fallback), `_extract_real_reply_text` (reply-body cleaning), `_strip_reasoning_tags`. `Message.status` flows through `models.py` (migration `0050_message_status`), `events/types.py`, `events/projection.py`, `serializers.py`.
- Frontend: `ChatInterface.tsx` — streaming timeline builder (`updateMessageSteps` dispatches, per-round thinking flush, tool-step append, `done` replacement); `chatSlice.ts` — new `updateMessageSteps` action; `ImmersiveChatWindow.tsx` — header removal, legacy-message step synthesis, incomplete-reply markers; `types/index.ts` + `utils/api.ts` — `Message.status` plumbing; `CreateCharacterSimplifiedForm.tsx` — avatar upload endpoint fix; i18n keys `replyIncomplete` / `replyInterrupted` (zh-CN + en-US).
- Deliberate semantics: client disconnect keeps already-streamed content (no background continuation); the draft is single-writer (the generation thread only); during streaming the `thinking` column holds the live system-think text, and the final message stores `thinking` = character OS, `raw_reasoning` = full system think.
