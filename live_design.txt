
可以做模式切换，不是“非要分开两种”，而是实现层最好分开，产品层可以合并。

你说的“模式切换”本质上有两层：

用户层
同一个聊天界面里切换 普通聊天 / 实时互动
这完全可以，也应该这样做
系统层
普通聊天是“请求-响应”
实时互动是“持续会话 + 双向事件流 + 可打断”
这两种底层机制差异很大，所以代码层最好不要硬揉成一个 handler
所以结论是：

UI 可以是一套
会话可以是一条
消息列表可以共用
但传输协议和编排逻辑最好分两套
为什么底层不建议强行合一

普通模式的特征：

用户发一条
后端生成一条
SSE/HTTP 流式返回就够了
状态简单
实时模式的特征：

麦克风持续进来
屏幕/摄像头持续进来
partial transcript 不断变化
角色可能边听边说
用户说一句就要打断
同时存在“采集、感知、生成、取消、恢复”
如果把这两种都塞进 backend/chat/views.py 这种 REST 流里，后面会很快变成：

一堆 if realtime
一堆事件状态分支
很难测
很难做打断
很难做多路输入同步
这就是我说“实现层分开，产品层合并”的原因。

更合理的做法

做一个统一的 Chat 页面，提供模式切换：

Text
Live
共享的部分：

同一个角色
同一个 session
同一个消息历史
同一个模型配置
同一套附件能力提示
分开的部分：

Text mode
继续走现有 stream_message
Live mode
走 WebSocket realtime session
也就是说，不是两个产品，而是一个页面里的两个运行模式。

建议的结构

前端：

frontend/src/components/ChatInterface.tsx
增加模式切换状态 chatMode: 'text' | 'live'
MessageList 共用
TextComposer 负责普通输入
LiveComposer 负责屏幕/摄像头/麦克风
后端：

普通模式保留现有：
/api/chat/stream_message/
实时模式新增：
/ws/chat/live/:sessionId
模型适配：

同一个 ModelConfiguration
但多一组 capability 字段
根据 mode 选择可用能力和降级策略
为什么这比“完全一套”更好

因为用户看到的是切模式，不是切系统。
但工程上你仍然保留清晰边界：

文本聊天稳定，不会被实时逻辑污染
实时模式可以单独优化打断、采样率、音频缓冲
出问题时容易定位
如果你坚持一套协议也不是不行

也可以做成“统一事件总线”：

普通消息也发成事件
实时音频/视频也是事件
后端统一 WebSocket
例如：

input.text
input.audio_chunk
input.video_frame
response.delta
response.done
response.cancel
这样从协议层是统一的。
但即便这样，内部还是会自然分成：

text turn processor
realtime processor
所以本质上还是“表面统一，内部拆开”。

最实际的答案

你完全可以做“模式切换”：

默认 文字模式
一键切到 实时模式
消息历史不断
角色不变
模型不变
不支持的能力自动降级
我反对的不是模式切换，我反对的是把两种运行时硬塞进同一个简单 HTTP 聊天处理器里。
